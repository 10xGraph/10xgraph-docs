Most of the technical controls a SOC 2, ISO 27001 or GDPR review asks for are built in: authentication with role-based access checked on every route, owner and tenant scoping in storage, a metadata-only audit log, rate limits, strict input rules, production boot checks, delete endpoints that also remove a thread's files, memory expiry, and a hardened image and Kubernetes manifest. The Full setup turns the main ones on. You host 10xGraph yourself, so your data stays in your infrastructure, and the server and libraries send nothing to 10xScale. Your organization brings the rest: policies, processes and the environment you run it in.

**In the 35 SOC 2 and ISO 27001 rows below, 21 are built in, 11 are partly built in and 3 stay with you. In the 8 GDPR rows, 3 are built in, 4 are partly built in and 1 stays with you.**

Each row names the feature, its default and what you own. Your auditor examines your organization and your deployment and decides what evidence is enough.

The control descriptions below are short paraphrases, not the official text. Check each one against the AICPA Trust Services Criteria (2017, with the 2022 revised points of focus), ISO/IEC 27001:2022 Annex A and Regulation (EU) 2016/679 (GDPR) before you cite it in an audit or a review.

## How to read the status

Each row starts with one of three statuses.

| Status | Meaning |
|---|---|
| Built in | 10xGraph provides the application-level control. What is left is configuration, policy, process or your environment (identity provider, network, TLS, storage). |
| Partly built in | 10xGraph provides part of the application-level control. The row names the missing piece. |
| Stays with you | 10xGraph has no feature for this control. It lives in your organization or infrastructure. |

## What the default Full setup turns on

`10xgraph init --mode full` with no other flags writes a `10xgraph.json` and a project with:

- Storage `memory`: the graph compiles with `InMemoryCheckpointer`. State is lost on restart.
- Auth `jwt`.
- A `memory` cache store.
- Rate limiting on: 100 requests per 60 seconds, by user, `fail_open: false`.
- Token revocation on (`token_revocation: true`).
- The audit log on, with `sinks: ["log"]` and `include_reads: true`.
- A `PromptInjectionValidator` registered on the graph.

Flags change this:

- `--storage postgres` gives `PgCheckpointer` and a Redis cache store. `--storage postgres-memory` adds `PgVectorStore`.
- `--storage sqlite` gives `SqliteCheckpointer` and keeps the memory cache store.
- `--worker` forces a Redis cache store.
- `--auth none` turns revocation off and rate limits by IP.

The Quick setup writes none of these settings.

With the memory cache store, rate limits, revocations, run locks and run caps hold per process, and the image from `10xgraph build` runs two workers (`WEB_CONCURRENCY=2`). See [Scaling and reliability](/docs/production/scaling#what-the-cache-store-shares-across-workers).

The Dockerfile, Compose file and Kubernetes manifest from `10xgraph build` set `MODE=production` and `LOG_FORMAT=json`. What production mode refuses at startup and what it changes is in the [security model](/docs/production/security-model#what-production-mode-refuses-at-startup).

## How to read the Default column

| Value | Meaning |
|---|---|
| on | Active without configuration, in any mode. |
| with auth | Active once `auth` is set (`jwt` or `custom`). Auth is off until you set it; the Full setup sets `jwt`. |
| Full setup | Written to `10xgraph.json` by `10xgraph init --mode full`. Absent otherwise until you add it. |
| `MODE=production` | Active when the server runs with `MODE=production`. The generated Dockerfile, Compose file and Kubernetes manifest set it. |
| generated deploy files | Set in the Dockerfile, Compose file or Kubernetes manifest that `10xgraph build` writes. |
| with Postgres storage | Needs `PgCheckpointer` (or `PgVectorStore`): `--storage postgres` or `postgres-memory`, or your own instance passed to `compile()`. |
| (shared cache store) | Added after another value. With the memory cache store it holds per process only. It holds across workers and replicas only with a Redis or custom shared cache store. |
| opt-in | Off until you enable it. |
| run by hand | A CLI command you run yourself. |
| n/a | No setting. The row describes a design property or your responsibility. |

Data leaves your infrastructure only to services you configure: model providers, MCP servers, tracing backends, publishers and Sentry. You choose the model provider, including Anthropic through Vertex AI or Bedrock and Gemini through Vertex AI. | on | Contracts (DPAs) with model providers and every other service you configure, their regions, transfer safeguards. | [Integrations](/docs/integrations), [Observability](/docs/observability) |
| Art. 33, 34 | Report a personal data breach and tell the people affected. | **Stays with you.** The audit log and request ids help you find what happened, and token revocation helps contain a leaked token. | Audit log: Full setup. Revocation: Full setup (shared cache store). | Breach detection, assessment and notification. | [Audit log](/docs/server/audit-log), [Auth](/docs/server/auth) |

`10xgraph dev` opens the hosted playground at play.10xgraph.com, a separate web app with its own usage analytics. It is a development tool: `--no-open` skips it, and the generated deploy files do not run it.

### What stays with you under GDPR

- The lawful basis for each processing purpose (Art. 6) and the privacy notice (Art. 13, 14).
- Contracts with model providers and every other service that receives personal data, and their regions.
- The data subject request process: verify who is asking, run the reads and deletes above, and answer in time.
- What personal data enters prompts, tool calls, memories, traces and publishers. Personal data inside prompts and model outputs is yours to classify: 10xGraph stores and forwards message content as your graph produces it and does not detect personal data in it.
- The retention schedule, and erasure in log storage, trace backends, publisher consumers and backups.
- The record of processing activities (Art. 30) and a data protection impact assessment where one is needed (Art. 35).

## Not provided by 10xGraph

An auditor may ask for these. They are not features of the server, or only partly. Each row says what to do.

| Evidence asked for | Status | What to do |
|---|---|---|
| Automatic retention for threads, messages and files (delete those older than N days) | Not provided | Memories can expire on their own (`ttl` on the memory config, removed by the `memory_cleanup` task). For threads, run your own job. The `PgCheckpointer` threads table has `created_at` and `updated_at`; SQLite has only `updated_at`; the in-memory checkpointer has neither. Deployer SQL or a scheduled [background task](/docs/guides/run-background-tasks) can select old threads. Delete through the thread delete path rather than raw SQL so files are released too. `state_history_limit` prunes snapshots only, and only in `PgCheckpointer`. |
| Erase everything for one user or tenant in one call | Partial | Per-thread delete with file and trace cleanup, memory forget by filter and file delete exist. A full erase means listing and deleting each thread, then memories and files. Script it against the [REST API](/docs/reference/rest-api/threads). |
| Export of one user's data | Partial | List and read endpoints cover threads, messages, memories and files. There is no single export call; script it. |
| JWKS URL fetch for identity provider keys | Not provided | Built-in `JwtAuth` verifies RS, ES, PS and EdDSA tokens with a static public key in `JWT_SECRET_KEY` or `JWT_SECRET_KEYS`. The `jwt` extra installs bare PyJWT, so install `cryptography` too. Keys rotate with `JWT_SECRET_KEYS` and `kid`. Only fetching keys from a JWKS URL is missing; a custom `BaseAuth` can do it. See [Auth](/docs/server/auth). |
| Encryption at rest | Your infrastructure | Use Postgres, disk and bucket encryption and your key management. The app does no field encryption. |
| PII redaction in logs and telemetry | Not provided | Only secrets are masked. Set the trace level to `spans` to keep content out of traces. A custom publisher can filter events before they leave. See [Use publishers](/docs/guides/use-publishers). |
| Malware scanning of uploads | Not provided | Uploads get signature, type and size checks. PDFs get a 10 MB and 500-page limit while `DOCUMENT_HANDLING=extract_text` (the default). Add a scanner in front of storage or in your upload path. |
| Backup and restore | Your infrastructure | Back up Postgres, Redis and object storage. See [Backup and restore](/docs/server/backup-and-restore). |
| MFA, user provisioning, access reviews | Your identity provider | 10xGraph verifies tokens and does not issue them. `GET /v1/me` shows the resolved access of a caller to support a review. |
| Per-run usage and cost record | Partial | Spans carry token counts at trace level `standard` or higher, and a `tenxgraph.llm.tokens` counter exists. Neither is a per-run record. See [Observability](/docs/observability). |

## Project practices

These are practices of the 10xGraph project itself, relevant to SDLC questions in vendor reviews. They are not controls of your deployment.

- A security policy with private vulnerability reporting. See [Security policy](/docs/project/security).
- Dependabot in all three repositories; CodeQL on the API server and the TypeScript client.
- CI runs lint, type checks and tests on every repository.

Not in place: signed releases, build provenance, PyPI trusted publishing, npm provenance, an SBOM, CodeQL on the core repository and dependency vulnerability audits in CI.
